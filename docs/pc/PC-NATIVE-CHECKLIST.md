# PC 原生验收清单（t18）

| 项目 | 内容 |
| --- | --- |
| 用途 | 把「像不像 PC 程序」变成可量化、可勾选、可复现的验收标准；用作 t15/t16/t17 的验收标尺与 t18 的核查台账 |
| 基准视口 | **1440×900 逻辑像素**（Windows 100% 缩放），副视口 1920×1080、2560×1440 |
| 反例基线 | `screenshots/tablet.png`（Android 平板 2560×1600）——凡照抄平板尺寸（大卡 224dp、行高 100dp、竖排导航 80dp、标题 28sp+）的，一律按「平板放大版」判 FAIL |
| 判定口径 | 每条只有 **PASS / FAIL / N/A / 未验证** 四态；FAIL 必须写「实际值、差值、证据、责任人」 |
| 责任分工 | 密度四页 → ui2（t15）；播放侧 → audio2（t16）；窗口装饰与交互底座 → win2（t17）；核查与台账 → qa2（t18） |
| 纪律 | 核查者**不改产品代码**；发现问题只登记、只提修复建议，交回对应成员 |
| 日期 | 2026-11-27（基于 t4 交付版本建立基线数值） |

> 为什么要有这份清单：前几轮验收只回答「功能有没有实现」，没回答「在 PC 上好不好用」。
> 平板尺寸体系（56dp 行高、32sp 页面标题、96dp 竖排导航、380dp 侧栏）在 1440×900 的桌面上
> 呈现为「平板界面放大版」，被用户否决。本清单把每一处「像平板」的尺寸换成可测数字。

## 0. 判定规则与测量方法

### 0.1 四态定义

| 状态 | 含义 | 使用条件 |
| --- | --- | --- |
| PASS | 达标 | 有截图测量值或代码位置（含单测）佐证 |
| FAIL | 不达标 | 必须同时给出：实际值、与标准的差值、证据、责任人 |
| N/A | 本轮不适用 | 必须写明理由（如功能未承诺、平台限制），由 captain 确认后生效 |
| 未验证 | 还没测 | 只在核查进行中使用，收尾时不允许残留 |

### 0.2 证据三选一（优先截图，其次代码，最后单测）

1. **截图**：`--screenshot` 离屏渲染（不开窗口、不抢焦点），文件名 + 测量值（如「行高实测 56px @100% 缩放」）。
2. **代码位置**：`文件:行`，如 `ui/components/Content.kt:206`（行高定义）。
3. **单测**：`类名#方法`，如 `WindowsIntegrationSmokeTest#悬浮窗样式不抢焦点`。

交互类（hover/右键/多选/快捷键）截图截不到，**必须**用「代码位置 + 单测」组合，并在条目的「验证」里注明
「截图不适用，以代码+单测为准」。

### 0.3 离屏截图命令（仓库外，固定目录）

```powershell
$env:JAVA_HOME="D:\env\.jdks\jdk-21.0.13.1+2"
$env:ANDROID_HOME="$env:LOCALAPPDATA\Android\Sdk"
./gradlew :desktop:run --args="--screenshot=F:/tmp/pc-native-check-<日期>"
```

- 截图落 `F:\tmp\pc-native-check-<日期>\`，不进仓库。
- **视口要求**：截图必须能按 1440×900 输出（现有 `--screenshot` 固定 1600×1000，见 `Main.kt:227-228`）。
  若本轮未支持视口参数，qa2 用 1600×1000 出图后按 1.111 比例换算，并在台账注明「换算值，非直接测量」。
  **此项由 ui2 在 t15 顺带增加 `--screenshot=dir:1440x900` 写法**（可选，不改也能换算）。
- 每个核查批次用新目录，不覆盖上一批。

### 0.4 尺寸测法

- Composable 尺寸以代码常量（`.height(56.dp)`）为准；截图测量用于验证「实际渲染是否等于常量」。
- 层数换算：100% 缩放 1dp = 1px；125% 缩放 1dp = 1.25px（高 DPI 项另测）。
- 行数断言以**完整可见行**计：被迷你条 / 窗口边缘裁掉一半的行不算。

## 1. 密度类（D）——硬指标

> 队长与 qa2 共同确定。1440×900 垂直预算（客户区）：
> 菜单栏 24 + 页面标题区 32 + 工具行 32 + 列表表头 24 + 迷你条 64 + 页边距 24 = **200dp**，
> 可用 700dp；行高 ≤36dp → **19.4 行 ≥ 18 行**。任何一项预算被突破，18 行都必须重算，
> 责任人要在 PR/提交里附新的算式。

## 6. 核查流程（qa2 执行）

1. **取产物**：等 t15/t16/t17 各自提交后，`git log --oneline -5` 确认提交号，记录到台账「核查批次」。
2. **出图**：`--screenshot` 离屏渲染到新目录（见 0.3），**不开窗口**；同时在 100% / 150% 两种缩放下各出一组（若工具支持 density 参数，否则只测 100% 并在台账注明）。
3. **逐项核**：D → I → W → P 顺序；D 类每项在截图上量值并填「实际值」；I/W 类读代码位置 + 跑相关单测。
4. **跑回归**：`./gradlew :desktop:test :playback-vlc:test`（Windows 集成冒烟 + 播放引擎），确认未回归。
5. **填台账**：更新 §5 登记表；新 FAIL 追加行；修好的标「已修（提交号）」。
6. **出结论**：写一段「本轮 PASS/FAIL 统计 + 阻塞项」发给 captain；**不改产品代码**。
7. **归档**：截图目录与日志路径写进结论；不提交进仓库。
